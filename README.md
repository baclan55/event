# Event Department Portal

Внутренний портал ивент-отдела: FAQ, состав сотрудников с иерархией ролей,
правила мероприятий, регламент, первые шаги для новичков, система выговоров
и заявки. Личный кабинет (вход по логину/паролю или через Discord) — в виде
компактного элемента в шапке, а не отдельной посадочной страницей.

Технологии: **Node.js + Express** (backend и API), **PostgreSQL** (для Neon),
чистый HTML/CSS/JS на фронтенде (без сборки, без фреймворков) — можно просто
залить на хостинг и запустить.

## Структура проекта

```
event-department-portal/
├── package.json
├── .env.example          — шаблон переменных окружения (скопировать в .env)
├── render.yaml            — blueprint для деплоя на Render
├── src/
│   ├── server.js          — точка входа Express-приложения
│   ├── db/
│   │   ├── schema.sql     — SQL-схема базы данных
│   │   ├── migrate.js     — применяет schema.sql (npm run db:migrate)
│   │   ├── seed.js        — создаёт роли, владельца, тексты по умолчанию
│   │   ├── pool.js        — подключение к PostgreSQL
│   │   └── images.js      — сохранение картинок в базу
│   ├── middleware/        — авторизация, загрузка файлов
│   └── routes/            — REST API (auth, content, rules, roster, ...)
└── public/                — весь фронтенд (отдаётся как статика)
    ├── index.html
    ├── css/style.css
    ├── img/mountains-bg.jpg
    └── js/                — vanilla JS, без сборки
```

Backend отдаёт и статику из `public/`, и JSON API из `/api/*` одним и тем же
Node-процессом — то есть на Render это **один Web Service**.

## Быстрый старт локально

### Требования

- Node.js 18 или новее (проверить: `node -v`)
- Доступ к PostgreSQL — либо локальный сервер, либо сразу база на Neon
  (см. следующий раздел — для локальной разработки можно сразу использовать
  Neon и не ставить Postgres на свой компьютер).

### Шаги

```bash
# 1. Установить зависимости
npm install

# 2. Скопировать файл с переменными окружения и заполнить его
cp .env.example .env
```

Откройте `.env` и укажите как минимум:

```
DATABASE_URL=postgresql://user:password@host/dbname?sslmode=require
SESSION_SECRET=любая-длинная-случайная-строка
OWNER_LOGIN=owner
OWNER_PASSWORD=придумайте-надёжный-пароль
OWNER_NICKNAME=Владелец
```

`DATABASE_URL` — либо строка подключения к вашему локальному Postgres
(`postgresql://postgres:postgres@localhost:5432/eventportal`), либо строка
из Neon (см. следующий раздел).

```bash
# 3. Создать таблицы и заполнить базу начальными данными
#    (роли, аккаунт владельца, заготовки текстов)
npm run setup

# 4. Запустить сервер
npm start
```

Откройте **http://localhost:3000** — увидите портал. Нажмите «Войти» в
правом верхнем углу и войдите под логином/паролем из `OWNER_LOGIN` /
`OWNER_PASSWORD` — этот аккаунт сразу имеет права владельца (доступ к
«Панели владельца» и редактированию всех разделов).

Для разработки с автоперезапуском при изменении файлов backend:

```bash
npm run dev
```

## Создание базы данных на Neon

[Neon](https://neon.tech) — облачный serverless-Postgres с бесплатным
тарифом, отлично сочетается с Render.

1. Зарегистрируйтесь на **neon.tech** и создайте новый проект (Project).
   Регион можно выбрать ближайший к региону вашего Render-сервиса.
2. В панели проекта откройте вкладку **Connection Details** / **Connect**.
3. Выберите вариант строки подключения для **psql / стандартного драйвера**
   (не «Pooled» и не «.env для Prisma» — просто обычная строка вида
   `postgresql://...`). Скопируйте её.
4. Строка должна заканчиваться на `?sslmode=require` — если Neon не добавил
   этот параметр сам, допишите его вручную.
5. Вставьте эту строку в `.env` (локально) или в переменные окружения
   Render (при деплое) как значение `DATABASE_URL`.
6. Примените схему и сид: локально это `npm run setup` при активной `.env`
   с этой строкой подключения (см. раздел деплоя ниже — то же самое нужно
   сделать один раз и для продакшен-базы).

Один и тот же проект Neon можно использовать и для локальной разработки,
и для продакшена — либо создать два отдельных проекта Neon (рекомендуется,
чтобы не путать тестовые данные с боевыми).

## Деплой на Render

### 1. Загрузите проект в Git-репозиторий

Render разворачивает сервисы из Git (GitHub/GitLab). Если ещё не сделали:

```bash
git init
git add .
git commit -m "Initial commit"
```

Создайте пустой репозиторий на GitHub и запушьте туда код (`git remote add
origin ...` и `git push`).

### 2. Создайте Web Service на Render

Вариант А — через Blueprint (быстрее): зайдите в Render → **New +** →
**Blueprint**, укажите ваш репозиторий. Render найдёт `render.yaml` и
предложит создать сервис с уже прописанными переменными (значения с
`sync: false` нужно будет ввести вручную — как раз `DATABASE_URL`,
`OWNER_LOGIN`, `OWNER_PASSWORD` и, если нужно, Discord-ключи).

Вариант Б — вручную: **New +** → **Web Service** → выберите репозиторий →

- **Runtime**: Node
- **Build Command**: `npm install`
- **Start Command**: `npm start`
- **Plan**: Free (или платный, по желанию)

### 3. Заполните переменные окружения

В разделе **Environment** сервиса добавьте те же переменные, что и в
`.env.example` (см. таблицу ниже). Обязательно:

- `DATABASE_URL` — строка подключения из Neon (см. выше)
- `SESSION_SECRET` — длинная случайная строка (Render может сгенерировать
  сам, если использовать `render.yaml`)
- `OWNER_LOGIN`, `OWNER_PASSWORD`, `OWNER_NICKNAME` — данные для входа
  первого администратора
- `NODE_ENV=production`

### 4. Примените схему БД и сид к продакшен-базе

Это нужно сделать один раз, **до первого открытия сайта** (или сразу
после первого деплоя). Проще всего — со своего компьютера:

```bash
# временно укажите в .env продакшен DATABASE_URL (строку из Neon,
# ту же, что вписали в Render), затем:
npm run setup
```

После этого можно вернуть в локальный `.env` вашу локальную строку
подключения — на продакшен-базу это не повлияет, `npm run setup` уже
создал в ней таблицы, роли и аккаунт владельца.

Альтернативный способ — вкладка **Shell** у сервиса на Render (доступна
после первого деплоя): там тоже можно выполнить `npm run setup` — она
использует `DATABASE_URL`, уже прописанный в переменных окружения Render.

### 5. Деплой

Render автоматически соберёт и запустит сервис после пуша в ветку (или по
кнопке **Manual Deploy**). После завершения деплоя откройте выданный Render
URL (`https://<ваш-сервис>.onrender.com`) — портал должен открыться.

> **Важно про диск:** контейнер Render не сохраняет файлы между деплоями и
> перезапусками. Поэтому все загружаемые картинки (аватары, иллюстрации к
> FAQ/правилам/регламенту) в этом проекте хранятся не на диске, а прямо в
> базе данных PostgreSQL — они не потеряются при передеплое.

## Вход через Discord (необязательно)

Если вход по логину/паролю достаточно — этот раздел можно пропустить,
кнопка «Войти через Discord» просто будет неактивна.

1. Откройте <https://discord.com/developers/applications> → **New
   Application** → задайте имя.
2. Слева откройте **OAuth2** → **General**. Скопируйте **Client ID** и
   **Client Secret**.
3. Там же, в **Redirects**, добавьте URL вида:
   `https://<ваш-домен>/api/auth/discord/callback`
   (для локальной разработки: `http://localhost:3000/api/auth/discord/callback`).
4. Впишите в переменные окружения (локально в `.env`, на Render — в
   Environment):
   ```
   DISCORD_CLIENT_ID=...
   DISCORD_CLIENT_SECRET=...
   DISCORD_REDIRECT_URI=https://<ваш-домен>/api/auth/discord/callback
   ```
5. Перезапустите сервер (`npm start` / redeploy на Render). Кнопка «Войти
   через Discord» в окне входа станет активной.

Новый пользователь, впервые вошедший через Discord, создаётся автоматически
с ролью «Mini Event Helper» и без прав администратора — выдать роль/права
можно в «Панели владельца».

## Роли и права доступа

В проекте два независимых понятия:

- **Роль в иерархии** (для отображения в «Составе»): Chief Event →
  Dep.Chief Event → Curator Event → Event Administrator → Chief Event
  Helper → Dep.Chief Event Helper → Senior Event Helper → Event Helper →
  Mini Event Helper. Чисто информационная — определяет сортировку и
  подпись в списке участников.
- **Флаги доступа**: `is_admin` (может редактировать разделы: FAQ,
  Регламент, Правила МП, Первые шаги, Состав, выговоры, рассматривать
  заявки) и `is_owner` (дополнительно — доступ к «Панели владельца»,
  где можно назначать/снимать права другим пользователям и менять пароли).

Аккаунт из `OWNER_LOGIN`/`OWNER_PASSWORD` создаётся при первом запуске
`npm run db:seed` сразу с обоими флагами. Все остальные регистрируются
самостоятельно (кнопка «Регистрация» в окне входа) с ролью «Mini Event
Helper» и без прав — владелец затем назначает им роль/права в «Панели
владельца».

## Как устроены разделы

- **FAQ** — переключатель «Event Helper» / «Event Administrator» сверху,
  под каждым — свой текст и своя картинка. Кнопка «Редактировать» видна
  только администраторам/владельцу.
- **Состав** — список всех сотрудников, отсортированный по иерархии (от
  Chief Event до Mini Event Helper). Справа от имени — счётчик мероприятий
  за неделю: зелёным, если ≥ нормы (по умолчанию 5, настраивается через
  `WEEKLY_EVENTS_TARGET`), красным — если меньше. Администратор может
  добавлять участников, менять роль/счётчик/аватар.
- **Правила МП** — список правил, у каждого свой заголовок, текст (суть
  правила) и картинка; администратор может добавлять/редактировать/удалять.
- **Регламент** — так же, как FAQ: переключатель Event Helper / Event
  Administrator, свой текст и картинка на каждую аудиторию.
- **Первые шаги** — один текст + одна картинка, без переключателя.
- **Система выговоров** — видна только администраторам/владельцу: список
  дисциплинарных записей на сотрудников с причиной и датой.
- **Заявки** — обычный вошедший сотрудник видит форму подачи заявки;
  администратор видит список всех заявок и может одобрить/отклонить.
- **Панель владельца** — только для владельца: список всех аккаунтов,
  назначение роли/прав администратора и владельца, сброс пароля, удаление.

## Переменные окружения

| Переменная | Обязательна | Описание |
|---|---|---|
| `DATABASE_URL` | да | Строка подключения к PostgreSQL (Neon) |
| `SESSION_SECRET` | да | Случайная строка для подписи сессий |
| `OWNER_LOGIN` / `OWNER_PASSWORD` / `OWNER_NICKNAME` | рекомендуется | Данные аккаунта владельца, создаётся при `npm run db:seed` |
| `APP_TITLE` / `APP_SUBTITLE` | нет | Название отдела, отображается в шапке |
| `WEEKLY_EVENTS_TARGET` | нет | Норма мероприятий в неделю (по умолчанию 5) |
| `DISCORD_CLIENT_ID` / `DISCORD_CLIENT_SECRET` / `DISCORD_REDIRECT_URI` | нет | Вход через Discord |
| `PORT` | нет | Порт сервера (Render подставляет автоматически) |
| `NODE_ENV` | нет | `production` на хостинге — включает secure-cookies |

## Частые проблемы

**«password authentication failed» / ошибка SSL при подключении к базе.**
Проверьте, что `DATABASE_URL` скопирован из Neon целиком, включая
`?sslmode=require`, и без лишних пробелов/переносов строк.

**После деплоя открывается пустая страница или ошибка 500.**
Скорее всего, схема ещё не применена к продакшен-базе — выполните
`npm run setup`, указав продакшен `DATABASE_URL` (см. «Деплой на Render»,
шаг 4).

**Не могу войти под owner-логином после деплоя.**
`npm run db:seed` создаёт владельца только один раз — если аккаунт с таким
логином уже существует, seed его не трогает и не обновляет пароль. Чтобы
сбросить пароль, войдите под другим владельцем и смените пароль через
«Панель владельца», либо очистите таблицу `users` и повторите `npm run
db:seed`.

**Картинки не сохраняются между деплоями на Render.**
Такого быть не должно — все картинки хранятся в самой базе PostgreSQL
(таблица `images`), а не на диске контейнера. Если картинка пропала,
проверьте, что `DATABASE_URL` в переменных окружения Render не менялся
(иначе сервис фактически «переключился» на другую базу).
