# Events Denver — Event Department Portal

Сайт ивент-отдела сервера Events Denver: публичная главная страница с
рассказом о роли Event Helper и формой заявки, плюс внутренний личный
кабинет для сотрудников — FAQ, состав, правила мероприятий, регламент,
первые шаги, система выговоров и рассмотрение заявок.

**Вход в личный кабинет только через Discord** — отдельной регистрации
логином/паролем в проекте нет.

Технологии: **Node.js + Express** (backend и API), **PostgreSQL** (для
Neon), чистый HTML/CSS/JS на фронтенде (без сборки, без фреймворков) —
можно просто залить на хостинг и запустить.

## Структура проекта

```
event-department-portal/
├── package.json
├── .env.example           — шаблон переменных окружения (скопировать в .env)
├── render.yaml             — blueprint для деплоя на Render
├── src/
│   ├── server.js           — точка входа Express-приложения
│   ├── db/
│   │   ├── schema.sql       — SQL-схема базы данных
│   │   ├── migrate.js       — применяет schema.sql (npm run db:migrate)
│   │   ├── seed.js          — создаёт роли, назначает владельца, тексты по умолчанию
│   │   ├── pool.js          — подключение к PostgreSQL
│   │   └── images.js        — сохранение картинок в базу
│   ├── middleware/          — авторизация, загрузка файлов
│   └── routes/               — REST API (auth, content, rules, roster, applications, ...)
└── public/                  — весь фронтенд (отдаётся как статика)
    ├── index.html
    ├── css/style.css
    ├── img/mountains-bg.jpg
    └── js/
        ├── site.js           — публичные страницы: Главная и Оставить заявку
        ├── app.js             — маршрутизация + личный кабинет (сайдбар)
        └── sections/          — разделы личного кабинета
```

Backend отдаёт и статику из `public/`, и JSON API из `/api/*` одним и тем же
Node-процессом — то есть на Render это **один Web Service**.

### Как устроена навигация

Сайт живёт в двух режимах:

- **Публичный сайт** (`#/home`, `#/apply`) — Главная страница и форма
  заявки. Доступны всем, без входа.
- **Личный кабинет** (`#/faq`, `#/roster`, `#/rules`, …) — внутренний
  портал с сайдбаром. Открывается по кнопке «Личный кабинет» (после входа
  через Discord); из сайдбара всегда можно вернуться на сайт по ссылке
  «На сайт».

## Быстрый старт локально

### Требования

- Node.js 18 или новее (проверить: `node -v`)
- Доступ к PostgreSQL — либо локальный сервер, либо сразу база на Neon
  (см. следующий раздел — для локальной разработки можно сразу использовать
  Neon и не ставить Postgres на свой компьютер).
- Приложение Discord для OAuth-входа (см. раздел [Настройка входа через
  Discord](#настройка-входа-через-discord)) — без него зайти в личный
  кабинет не получится, кнопка входа будет неактивна.

### Шаги

```bash
# 1. Установить зависимости
npm install

# 2. Скопировать файл с переменными окружения и заполнить его
cp .env.example .env
```

Откройте `.env` и укажите как минимум:

```
DATABASE_URL=postgresql://user:password@host/dbname?sslmode=require
SESSION_SECRET=любая-длинная-случайная-строка
DISCORD_CLIENT_ID=...
DISCORD_CLIENT_SECRET=...
DISCORD_REDIRECT_URI=http://localhost:3000/api/auth/discord/callback
DISCORD_OWNER_ID=ваш-discord-id
```

`DATABASE_URL` — либо строка подключения к вашему локальному Postgres
(`postgresql://postgres:postgres@localhost:5432/eventportal`), либо строка
из Neon (см. следующий раздел).

```bash
# 3. Создать таблицы и заполнить базу начальными данными (роли, тексты)
npm run setup

# 4. Запустить сервер
npm start
```

Откройте **http://localhost:3000** — увидите главную страницу сайта.
Нажмите «Личный кабинет» и войдите через Discord — если ваш Discord ID
совпадает с `DISCORD_OWNER_ID` из `.env`, вы сразу получите права
владельца (доступ к «Панели владельца» и редактированию всех разделов).

Для разработки с автоперезапуском при изменении файлов backend:

```bash
npm run dev
```

## Создание базы данных на Neon

[Neon](https://neon.tech) — облачный serverless-Postgres с бесплатным
тарифом, отлично сочетается с Render.

1. Зарегистрируйтесь на **neon.tech** и создайте новый проект (Project).
   Регион можно выбрать ближайший к региону вашего Render-сервиса.
2. В панели проекта откройте вкладку **Connection Details** / **Connect**.
3. Выберите вариант строки подключения для **psql / стандартного драйвера**
   (не «Pooled» и не «.env для Prisma» — просто обычная строка вида
   `postgresql://...`). Скопируйте её.
4. Строка должна заканчиваться на `?sslmode=require` — если Neon не добавил
   этот параметр сам, допишите его вручную.
5. Вставьте эту строку в `.env` (локально) или в переменные окружения
   Render (при деплое) как значение `DATABASE_URL`.
6. Примените схему и сид: локально это `npm run setup` при активной `.env`
   с этой строкой подключения (см. раздел деплоя ниже — то же самое нужно
   сделать один раз и для продакшен-базы).

Один и тот же проект Neon можно использовать и для локальной разработки,
и для продакшена — либо создать два отдельных проекта Neon (рекомендуется,
чтобы не путать тестовые данные с боевыми).

## Настройка входа через Discord

Вход в личный кабинет возможен **только через Discord** — этот шаг
обязателен, без него кнопка «Войти через Discord» будет неактивной.

1. Откройте <https://discord.com/developers/applications> → **New
   Application** → задайте имя.
2. Слева откройте **OAuth2** → **General**. Скопируйте **Client ID** и
   **Client Secret**.
3. Там же, в **Redirects**, добавьте URL вида:
   `https://<ваш-домен>/api/auth/discord/callback`
   (для локальной разработки: `http://localhost:3000/api/auth/discord/callback`).
4. Впишите в переменные окружения (локально в `.env`, на Render — в
   Environment):
   ```
   DISCORD_CLIENT_ID=...
   DISCORD_CLIENT_SECRET=...
   DISCORD_REDIRECT_URI=https://<ваш-домен>/api/auth/discord/callback
   ```
5. Перезапустите сервер (`npm start` / redeploy на Render). Кнопка «Войти
   через Discord» в окне входа станет активной.

### Как назначить владельца

Владелец назначается по **Discord ID**, а не логином/паролем:

1. Узнайте свой Discord ID: Discord → Настройки пользователя → Расширенные
   → включите «Режим разработчика», затем ПКМ по своему профилю →
   «Копировать ID пользователя».
2. Впишите его в переменную `DISCORD_OWNER_ID` (в `.env` локально или в
   Environment на Render) и перезапустите сервер.
3. Войдите через Discord — этот аккаунт автоматически получит права
   владельца (`is_owner` и `is_admin`), при каждом входе права
   синхронизируются заново, так что потерять их нельзя.

Если база данных совсем пустая (новый деплой, ни одного пользователя ещё
нет), владельцем автоматически станет первый, кто войдёт через Discord —
это подстраховка на случай, если `DISCORD_OWNER_ID` ещё не задан.

Все остальные, кто впервые входит через Discord, получают роль «Mini Event
Helper» без прав администратора — владелец затем выдаёт роль/права в
«Панели владельца».

## Деплой на Render

### 1. Загрузите проект в Git-репозиторий

Render разворачивает сервисы из Git (GitHub/GitLab). Если ещё не сделали:

```bash
git init
git add .
git commit -m "Initial commit"
```

Создайте пустой репозиторий на GitHub и запушьте туда код (`git remote add
origin ...` и `git push`).

### 2. Создайте Web Service на Render

Вариант А — через Blueprint (быстрее): зайдите в Render → **New +** →
**Blueprint**, укажите ваш репозиторий. Render найдёт `render.yaml` и
предложит создать сервис с уже прописанными переменными (значения с
`sync: false` нужно будет ввести вручную — `DATABASE_URL`,
`DISCORD_OWNER_ID` и Discord-ключи).

Вариант Б — вручную: **New +** → **Web Service** → выберите репозиторий →

- **Runtime**: Node
- **Build Command**: `npm install`
- **Start Command**: `npm start`
- **Plan**: Free (или платный, по желанию)

### 3. Заполните переменные окружения

В разделе **Environment** сервиса добавьте те же переменные, что и в
`.env.example` (см. таблицу ниже). Обязательно:

- `DATABASE_URL` — строка подключения из Neon (см. выше)
- `SESSION_SECRET` — длинная случайная строка (Render может сгенерировать
  сам, если использовать `render.yaml`)
- `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_REDIRECT_URI` —
  вход через Discord (redirect URI указывает на ваш домен на Render)
- `DISCORD_OWNER_ID` — ваш Discord ID, чтобы получить права владельца
- `NODE_ENV=production`

### 4. Примените схему БД и сид к продакшен-базе

Это нужно сделать один раз, **до первого открытия сайта** (или сразу
после первого деплоя). Проще всего — со своего компьютера:

```bash
# временно укажите в .env продакшен DATABASE_URL (строку из Neon,
# ту же, что вписали в Render), затем:
npm run setup
```

После этого можно вернуть в локальный `.env` вашу локальную строку
подключения — на продакшен-базу это не повлияет, `npm run setup` уже
создал в ней таблицы и роли.

Альтернативный способ — вкладка **Shell** у сервиса на Render (доступна
после первого деплоя): там тоже можно выполнить `npm run setup` — она
использует `DATABASE_URL`, уже прописанный в переменных окружения Render.

### 5. Деплой

Render автоматически соберёт и запустит сервис после пуша в ветку (или по
кнопке **Manual Deploy**). После завершения деплоя откройте выданный Render
URL (`https://<ваш-сервис>.onrender.com`) — должна открыться главная
страница сайта.

Не забудьте добавить `https://<ваш-сервис>.onrender.com/api/auth/discord/callback`
в **Redirects** приложения на Discord Developer Portal — иначе вход будет
падать с ошибкой `redirect_uri`.

> **Важно про диск:** контейнер Render не сохраняет файлы между деплоями и
> перезапусками. Поэтому все загружаемые картинки (аватары, иллюстрации к
> FAQ/правилам/регламенту) в этом проекте хранятся не на диске, а прямо в
> базе данных PostgreSQL — они не потеряются при передеплое.

## Роли и права доступа

В проекте два независимых понятия:

- **Роль в иерархии** (назначается в «Составе»): Chief Event →
  Dep.Chief Event → Curator Event → Event Administrator → Chief Event
  Helper → Dep.Chief Event Helper → Senior Event Helper → Event Helper →
  Mini Event Helper. Новый сотрудник, впервые вошедший через Discord,
  остаётся **«Без роли»**, пока администратор не назначит её вручную в
  «Составе» — до этого момента личный кабинет для него полностью закрыт
  (см. таблицу ниже).
- **Флаги** `is_admin` / `is_owner` — отвечают за право РЕДАКТИРОВАТЬ
  содержимое (FAQ, Регламент, Правила МП, Первые шаги) и
  добавлять/изменять участников в «Составе». С ролью в иерархии они не
  связаны напрямую.

Доступ к самим РАЗДЕЛАМ личного кабинета настроен по названию роли (см.
`src/utils/access.js` на бэкенде и его зеркало `public/js/access.js` на
фронтенде — оба списка нужно менять вместе):

| Раздел | Кому открыт |
|---|---|
| Моя страница, FAQ, Состав, Правила МП, Регламент, Первые шаги | Любому сотруднику с назначенной ролью |
| Система выговоров | Chief Event Helper, Dep.Chief Event Helper, Senior Event Helper, Chief Event, Dep.Chief Event |
| Заявки | Chief Event Helper, Dep.Chief Event Helper, Chief Event, Dep.Chief Event |
| Панель владельца | Chief Event, Dep.Chief Event |

Сотрудник «без роли» не видит в личном кабинете ни одного раздела —
вместо них показывается сообщение, что роль ещё не назначена.

Владелец назначается через `DISCORD_OWNER_ID` (см. [Как назначить
владельца](#как-назначить-владельца)) и при входе автоматически получает
не только `is_owner`/`is_admin`, но и высшую роль в иерархии (Chief
Event) — поэтому доступ ко всем разделам выше у него есть сразу.

## Как устроены разделы

### Публичный сайт

- **Главная** (`#/home`) — рассказ о роли Event Helper: что предлагает
  отдел, что требуется от кандидата, важная информация и кнопки перехода
  в Discord-сообщество (`https://discord.gg/eventsdenver`) и к форме
  заявки.
- **Оставить заявку** (`#/apply`) — форма из восьми обязательных полей
  (Discord, игровой Nickname и StaticID, возраст, среднесуточный онлайн,
  промежуток времени в игре, опыт, идеи по мероприятиям, мотивация).
  Отправка не требует входа. Если задан `APPLICATIONS_WEBHOOK_URL`, в
  указанный Discord-канал сразу приходит уведомление о новой заявке
  (с кликабельным упоминанием, если в поле Discord указан числовой ID).

### Личный кабинет

- **Моя страница** — личная мини-страница сотрудника, видна каждому с
  назначенной ролью (см. таблицу доступа выше): его собственный счётчик
  мероприятий за неделю (с той же зелёной/красной подсветкой нормы, что и
  в «Составе») и список его собственных выговоров с лимитами по тиру —
  без доступа к чужим записям и без открытия полного раздела «Система
  выговоров» (тот открыт только части ролей, см. ниже).
- **FAQ** — переключатель «Event Helper» / «Event Administrator» сверху,
  под каждым — свой текст и своя картинка. Кнопка «Редактировать» видна
  только администраторам/владельцу.
- **Состав** — список всех сотрудников, отсортированный по иерархии (от
  Chief Event до Mini Event Helper). Справа от имени — счётчик мероприятий
  за неделю: зелёным, если ≥ нормы (по умолчанию 5, настраивается через
  `WEEKLY_EVENTS_TARGET`), красным — если меньше. Администратор может
  добавлять участников, менять роль/счётчик/аватар.
- **Правила МП** — список правил, у каждого свой заголовок, текст (суть
  правила) и картинка; администратор может добавлять/редактировать/удалять.
- **Регламент** — так же, как FAQ: переключатель Event Helper / Event
  Administrator, свой текст и картинка на каждую аудиторию.
- **Первые шаги** — один текст + одна картинка, без переключателя.
- **Система выговоров** — видна только ролям из таблицы доступа выше:
  список дисциплинарных записей на сотрудников с причиной и датой.
- **Заявки** — видна только ролям из таблицы доступа выше: список заявок,
  поданных через публичную форму «Оставить заявку», с возможностью
  одобрить/отклонить/удалить.
- **Панель владельца** — видна только Chief Event и Dep.Chief Event:
  список всех аккаунтов, назначение роли/прав администратора и владельца,
  удаление.

## Переменные окружения

| Переменная | Обязательна | Описание |
|---|---|---|
| `DATABASE_URL` | да | Строка подключения к PostgreSQL (Neon) |
| `SESSION_SECRET` | да | Случайная строка для подписи сессий |
| `DISCORD_CLIENT_ID` / `DISCORD_CLIENT_SECRET` / `DISCORD_REDIRECT_URI` | да | Вход через Discord — без них зайти в личный кабинет нельзя |
| `DISCORD_OWNER_ID` | рекомендуется | Discord ID аккаунта, который автоматически получает права владельца при входе |
| `APPLICATIONS_WEBHOOK_URL` | нет | Discord Webhook для уведомлений о новых заявках |
| `APP_TITLE` / `APP_SUBTITLE` | нет | Название отдела, отображается в личном кабинете |
| `WEEKLY_EVENTS_TARGET` | нет | Норма мероприятий в неделю (по умолчанию 5) |
| `PORT` | нет | Порт сервера (Render подставляет автоматически) |
| `NODE_ENV` | нет | `production` на хостинге — включает secure-cookies |

## Частые проблемы

**«password authentication failed» / ошибка SSL при подключении к базе.**
Проверьте, что `DATABASE_URL` скопирован из Neon целиком, включая
`?sslmode=require`, и без лишних пробелов/переносов строк.

**После деплоя открывается пустая страница или ошибка 500.**
Скорее всего, схема ещё не применена к продакшен-базе — выполните
`npm run setup`, указав продакшен `DATABASE_URL` (см. «Деплой на Render»,
шаг 4).

**Кнопка «Войти через Discord» неактивна.**
Значит `DISCORD_CLIENT_ID`/`DISCORD_CLIENT_SECRET` не заданы на сервере —
добавьте их в `.env` (локально) или в Environment (на Render) и
перезапустите сервис.

**Вход через Discord падает с ошибкой `redirect_uri`.**
`DISCORD_REDIRECT_URI` в переменных окружения должен **точно** совпадать
(включая `http`/`https` и путь) со значением, добавленным в **Redirects**
на странице OAuth2 вашего приложения в Discord Developer Portal.

**Я вошёл через Discord, но нет прав владельца.**
Проверьте, что `DISCORD_OWNER_ID` в переменных окружения совпадает с вашим
реальным Discord ID (числовой ID, не username), и войдите заново — права
синхронизируются при каждом входе. Также можно выполнить `npm run db:seed`
после того, как переменная задана правильно — это назначит владельца, если
вы уже когда-то входили.

**Картинки не сохраняются между деплоями на Render.**
Такого быть не должно — все картинки хранятся в самой базе PostgreSQL
(таблица `images`), а не на диске контейнера. Если картинка пропала,
