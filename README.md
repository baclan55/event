# Events Denver — Event Department Portal

Сайт ивент-отдела сервера Events Denver: публичная главная страница с
рассказом о роли Event Helper и формой заявки, плюс внутренний личный
кабинет для сотрудников — FAQ, состав, правила мероприятий, регламент,
первые шаги, система выговоров и рассмотрение заявок.

**Вход в личный кабинет только через Discord** — отдельной регистрации
логином/паролем в проекте нет.

Технологии: **Node.js + Express** (backend и API), **PostgreSQL** (для
Neon), чистый HTML/CSS/JS на фронтенде (без сборки, без фреймворков) —
можно просто залить на хостинг и запустить.

### Как устроена навигация

Сайт живёт в двух режимах:

- **Публичный сайт** (`#/home`, `#/apply`) — Главная страница и форма
  заявки. Доступны всем, без входа.
- **Личный кабинет** (`#/faq`, `#/roster`, `#/rules`, …) — внутренний
  портал с сайдбаром. Открывается по кнопке «Личный кабинет» (после входа
  через Discord); из сайдбара всегда можно вернуться на сайт по ссылке
  «На сайт».

## Быстрый старт локально

### Требования

- Node.js 18 или новее (проверить: `node -v`)
- Доступ к PostgreSQL — либо локальный сервер, либо сразу база на Neon
  (см. следующий раздел — для локальной разработки можно сразу использовать
  Neon и не ставить Postgres на свой компьютер).
- Приложение Discord для OAuth-входа (см. раздел [Настройка входа через
  Discord](#настройка-входа-через-discord)) — без него зайти в личный
  кабинет не получится, кнопка входа будет неактивна.

### Шаги

```bash
# 1. Установить зависимости
npm install

# 2. Скопировать файл с переменными окружения и заполнить его
cp .env.example .env
```

Откройте `.env` и укажите как минимум:

```
DATABASE_URL=postgresql://user:password@host/dbname?sslmode=require
SESSION_SECRET=любая-длинная-случайная-строка
DISCORD_CLIENT_ID=...
DISCORD_CLIENT_SECRET=...
DISCORD_REDIRECT_URI=http://localhost:3000/api/auth/discord/callback
DISCORD_OWNER_ID=ваш-discord-id
```

`DATABASE_URL` — либо строка подключения к вашему локальному Postgres
(`postgresql://postgres:postgres@localhost:5432/eventportal`), либо строка
из Neon (см. следующий раздел).

```bash
# 3. Создать таблицы и заполнить базу начальными данными (роли, тексты)
npm run setup

# 4. Запустить сервер
npm start
```

Откройте **http://localhost:3000** — увидите главную страницу сайта.
Нажмите «Личный кабинет» и войдите через Discord — если ваш Discord ID
совпадает с `DISCORD_OWNER_ID` из `.env`, вы сразу получите права
владельца (доступ к «Панели владельца» и редактированию всех разделов).

Для разработки с автоперезапуском при изменении файлов backend:

```bash
npm run dev
```

## Создание базы данных на Neon

[Neon](https://neon.tech) — облачный serverless-Postgres с бесплатным
тарифом, отлично сочетается с Render.

1. Зарегистрируйтесь на **neon.tech** и создайте новый проект (Project).
   Регион можно выбрать ближайший к региону вашего Render-сервиса.
2. В панели проекта откройте вкладку **Connection Details** / **Connect**.
3. Выберите вариант строки подключения для **psql / стандартного драйвера**
   (не «Pooled» и не «.env для Prisma» — просто обычная строка вида
   `postgresql://...`). Скопируйте её.
4. Строка должна заканчиваться на `?sslmode=require` — если Neon не добавил
   этот параметр сам, допишите его вручную.
5. Вставьте эту строку в `.env` (локально) или в переменные окружения
   Render (при деплое) как значение `DATABASE_URL`.
6. Примените схему и сид: локально это `npm run setup` при активной `.env`
   с этой строкой подключения (см. раздел деплоя ниже — то же самое нужно
   сделать один раз и для продакшен-базы).

Один и тот же проект Neon можно использовать и для локальной разработки,
и для продакшена — либо создать два отдельных проекта Neon (рекомендуется,
чтобы не путать тестовые данные с боевыми).

## Настройка входа через Discord

Вход в личный кабинет возможен **только через Discord** — этот шаг
обязателен, без него кнопка «Войти через Discord» будет неактивной.

1. Откройте <https://discord.com/developers/applications> → **New
   Application** → задайте имя.
2. Слева откройте **OAuth2** → **General**. Скопируйте **Client ID** и
   **Client Secret**.
3. Там же, в **Redirects**, добавьте URL вида:
   `https://<ваш-домен>/api/auth/discord/callback`
   (для локальной разработки: `http://localhost:3000/api/auth/discord/callback`).
4. Впишите в переменные окружения (локально в `.env`, на Render — в
   Environment):
   ```
   DISCORD_CLIENT_ID=...
   DISCORD_CLIENT_SECRET=...
   DISCORD_REDIRECT_URI=https://<ваш-домен>/api/auth/discord/callback
   ```
5. Перезапустите сервер (`npm start` / redeploy на Render). Кнопка «Войти
   через Discord» в окне входа станет активной.

### Как назначить владельца

Владелец назначается по **Discord ID**, а не логином/паролем:

1. Узнайте свой Discord ID: Discord → Настройки пользователя → Расширенные
   → включите «Режим разработчика», затем ПКМ по своему профилю →
   «Копировать ID пользователя».
2. Впишите его в переменную `DISCORD_OWNER_ID` (в `.env` локально или в
   Environment на Render) и перезапустите сервер.
3. Войдите через Discord — этот аккаунт автоматически получит права
   владельца (`is_owner` и `is_admin`), при каждом входе права
   синхронизируются заново, так что потерять их нельзя.

Если база данных совсем пустая (новый деплой, ни одного пользователя ещё
нет), владельцем автоматически станет первый, кто войдёт через Discord —
это подстраховка на случай, если `DISCORD_OWNER_ID` ещё не задан.

Все остальные, кто впервые входит через Discord, получают роль «Mini Event
Helper» без прав администратора — владелец затем выдаёт роль/права в
«Панели владельца».

## Аватары через Cloudinary (опционально)

По умолчанию аватары (как и все остальные картинки на сайте — FAQ,
Правила, Регламент) хранятся прямо в базе Postgres, в таблице `images`.
Это надёжно, но занимает место в базе и не даёт CDN/оптимизации.

Если хотите отдавать аватары через [Cloudinary](https://cloudinary.com/)
(есть бесплатный тариф), это включается без изменений в коде — только
через переменные окружения. Как только они заданы, новые загруженные
аватары автоматически идут в Cloudinary; если переменные не заданы —
всё продолжает работать по-старому (в базе). Это касается **только
аватаров сотрудников** — картинки в FAQ/Правилах/Регламенте по-прежнему
хранятся в базе.

1. Зарегистрируйтесь на <https://cloudinary.com/users/register/free> и
   откройте **Dashboard** — там сразу видны **Cloud name**, **API Key**
   и **API Secret**.
2. Впишите их в переменные окружения (локально в `.env`, на Render — в
   Environment) любым из двух способов:
   ```
   # Вариант 1 — три отдельные переменные:
   CLOUDINARY_CLOUD_NAME=...
   CLOUDINARY_API_KEY=...
   CLOUDINARY_API_SECRET=...

   # Вариант 2 — одна строка (её тоже показывает Dashboard Cloudinary):
   CLOUDINARY_URL=cloudinary://<api_key>:<api_secret>@<cloud_name>
   ```
3. Перезапустите сервер (`npm start` / redeploy на Render). Проверить
   можно, загрузив себе новый аватар в разделе «Моя страница» — если всё
   настроено верно, картинка откроется по адресу вида
   `https://res.cloudinary.com/<cloud_name>/...`, а не `/media/...`.

При загрузке нового аватара старый файл в Cloudinary удаляется
автоматически, чтобы не копить лишнее в аккаунте. Аватары, загруженные
**до** подключения Cloudinary, никуда не пропадают и продолжают
отображаться из базы — им не обязательно быть перезалитыми.

## Discord-бот учёта посещаемости мероприятий

Опциональная функция: бот, встроенный в тот же процесс, что и сайт (не
нужен отдельный хостинг). Он следит за каналом, в котором бот сервера
публикует сообщения о сборе на мероприятие, и когда сбор **закрывается**
(в сообщении появляется подтверждённый список участников и «Победитель:»),
автоматически прибавляет **+1** к счётчику `weekly_events` («Состав», «X /
нед.») каждому участнику, который найден в «Составе» по своему Discord ID.
Если участник не зарегистрирован в «Составе» (не сотрудник, обычный
игрок) — он просто пропускается, начисление продолжается для остальных.

Логика реализована в `src/bot/eventAttendanceBot.js`. Она не привязана
жёстко к конкретному оформлению сообщения (embed или новые компоненты) —
ищет по всему тексту сообщения фразы-маркеры закрытия сбора и вытаскивает
Discord ID из раздела «Участники:». Каждое сообщение учитывается только
один раз (таблица `event_bot_processed_messages`), поэтому повторные
редактирования того же сообщения или перезапуск бота не приведут к
задвоению начислений. При старте бот также проверяет последние сообщения
канала — если сбор закрыли, пока сайт «спал» (например, бесплатный план
Render усыпляет неактивный сервис), это начисление не потеряется.

### Настройка

1. Откройте <https://discord.com/developers/applications> → **New
   Application** (можно использовать то же приложение, что и для входа
   через Discord, а можно отдельное — не принципиально).
2. Слева откройте **Bot** → **Add Bot** (если ещё не создан).
3. Там же включите переключатель **Message Content Intent** — без него бот
   не сможет прочитать текст сообщений с списком участников.
4. Скопируйте **Token** (кнопка **Reset Token**, если токен ещё не
   генерировался) — это значение переменной `DISCORD_BOT_TOKEN`.
5. Пригласите бота на сервер: **OAuth2** → **URL Generator** → в **Scopes**
   отметьте `bot`, в **Bot Permissions** достаточно **View Channel** и
   **Read Message History** (писать в канал боту не нужно). Откройте
   сгенерированную ссылку и добавьте бота на сервер.
6. Убедитесь, что у бота есть доступ к каналу со сборами (ID
   `1446581838100430878` по умолчанию) — если канал приватный/ограничен
   правами, добавьте боту соответствующую роль или разрешение вручную в
   настройках канала.
7. Впишите переменные окружения (локально в `.env`, на Render — в
   Environment):
   ```
   DISCORD_BOT_TOKEN=...
   ```
   Остальные переменные ниже уже настроены на ваш канал и вашего
   бота-источника по умолчанию — задавайте их, только если что-то из этого
   изменится:
   ```
   DISCORD_EVENTS_CHANNEL_ID=1446581838100430878
   DISCORD_EVENTS_SOURCE_BOT_ID=1468289401795903690
   EVENT_BOT_CATCHUP_LIMIT=50
   ```
8. Перезапустите сервер (`npm start` / redeploy на Render). В логах должно
   появиться `[event-bot] Подключен как <имя бота>. Слежу за каналом ...`.
   Если `DISCORD_BOT_TOKEN` не задан — бот просто не запускается, это не
   ошибка, остальной сайт продолжает работать как обычно.

### Как проверить, что работает

Закройте тестовый сбор на мероприятие в отслеживаемом канале и посмотрите
логи сервера — должна появиться строка вида `Сбор "..." закрыт: участников
найдено N, начислено M.`. Затем откройте «Состав» на сайте — у участников
счётчик должен вырасти на 1. Если кого-то не начислило — скорее всего, у
этого человека ещё не заполнен `discord_id` в «Составе» (это происходит
автоматически при первом входе через Discord на сайт).

> **На заметку:** засчитывается и администратор, который вёл сбор (раздел
> «Администратор:»), и все, кто в разделе «Участники:» — каждому по +1,
> независимо от роли.

### Исправленный баг: засчитывало не всех участников

В более ранней версии бота защита от повторного начисления была устроена
по ВСЕМУ сообщению целиком: как только текст сообщения хоть раз совпадал с
маркером «сбор закрыт», сообщение навсегда помечалось обработанным, и все
дальнейшие его редактирования бот больше не смотрел. Если маркер
срабатывал раньше, чем ожидалось (например, в самом начале, когда в
сообщении уже виден «Администратор:», а раздел «Участники:» ещё
пополняется) — начисление уходило только тем, кто уже был в списке на тот
момент (часто это был только сам администратор), а все, кто записывался
позже, никогда не засчитывались. Это и есть то поведение, которое вы
могли наблюдать: администратора видно на сайте сразу, а часть участников
— нет.

Начиная с этой версии защита от повторного начисления работает на уровне
**каждого отдельного участника**, а не всего сообщения (таблица
`event_bot_credits`). Сообщение можно безопасно обрабатывать сколько
угодно раз подряд — заново засчитаны будут только те, кому за это
конкретное сообщение ещё не начисляли; тем, кто в списке появится позже,
начисление придёт при следующей же проверке. Это не только чинит проблему
на будущее, но и **само «долечивает» уже виденные сборы**: при перезапуске
бот заново проходит по последним `EVENT_BOT_CATCHUP_LIMIT` сообщениям
канала (по умолчанию 50, максимум 100) и дозачисляет всех, кого не хватало
— вручную ничего чинить не нужно, если сбор попадает в это окно.

**Что нужно сделать, чтобы применить исправление:**

1. Примените обновлённую схему БД — добавляет таблицу `event_bot_credits`:
   ```
   npm run db:migrate
   ```
   (на проде — то же самое, что и при первой настройке: либо со своего
   компьютера с продакшен-`DATABASE_URL`, либо через вкладку **Shell** на
   Render).
2. Задеплойте обновлённый код и перезапустите сервис. При старте бот сам
   пройдёт по последним сообщениям канала и дозачислит всех, кого не
   хватало — смотрите логи (`[event-bot] ... новых начислений N`).

**Если сбор, который нужно долечить, старше окна `EVENT_BOT_CATCHUP_LIMIT`**
(например, это было давно, а канал активный), запустите разовый скрипт,
который проходит вглубь истории канала настолько далеко, насколько нужно:
```
npm run event-bot:backfill
# или указать своё число сообщений вглубь истории, по умолчанию 2000:
npm run event-bot:backfill -- 8000
```
Скрипт использует ту же идемпотентную логику — прогнать его повторно или
на уже здоровых данных полностью безопасно, лишний +1 никому не прилетит.

### Второй исправленный баг: доставало не того администратора и 0 участников

Отдельно от бага выше — в `collectStrings` (сборщик текста из embed'ов)
порядок ключей был `[..., 'value', 'name', 'label']`. Поле embed'а имеет
форму `{ name: "Администратор:", value: "Rei | 123..." }` — `value` это
содержимое, `name` его заголовок. Из-за того что `value` в списке шёл
раньше `name`, для каждого поля в итоговый текст сначала попадало
значение, а его заголовок — только после. Текст сообщения получался
перепутанным: значение поля «Администратор» — заголовок «Администратор:»
— значение поля «Участники» — заголовок «Участники:» — ... А
`extractAdminId`/`extractParticipantIds` ищут ID сразу **после**
заголовка секции — в перепутанном тексте после «Администратор:» стоял уже
ID **первого участника** (не администратора), а раздел «Участники:» к
этому моменту оставался пустым. Результат — начислялся +1 только одному
человеку (тому, кто первый в списке участников), причём записывался он в
базу как «администратор», а не как участник. Остальные не получали ничего.

Исправлено: заголовок (`name`/`label`) теперь всегда кладётся в текст
**перед** его значением (`value`), независимо от порядка ключей в
объекте. Если у вас уже стоит версия с первым исправлением (леджер
`event_bot_credits`), но баг всё ещё выглядит как «начисляет только
одному» — вам нужно именно это исправление, задеплойте обновлённый
`src/bot/eventAttendanceBot.js` и перезапустите сервис; встроенная
догонялка при старте дозачислит недостающих по последним сборам
автоматически.

### Еженедельный сброс счётчика «МП в неделю»

Счётчик `weekly_events` (виден на «Составе» и в «Дашборде» как «X / нед.»)
автоматически обнуляется у **всех** сотрудников в начале каждой недели —
в ночь с воскресенья на понедельник, ровно в 00:00 по времени,
заданному переменной `WEEKLY_RESET_TZ` (по умолчанию `Europe/Moscow`).
После сброса начисления бота учёта посещаемости (см. выше) снова
считаются с нуля.

Логика — в `src/utils/weeklyReset.js`: раз в минуту сервер проверяет, не
началась ли новая неделя с момента последнего сброса (момент сброса
хранится в таблице `weekly_reset_state`, а не в памяти процесса). Это
сделано специально, чтобы сброс не потерялся и не задвоился при
перезапуске сервера или при пробуждении сервиса после простоя (актуально
для бесплатного тарифа Render, который засыпает без трафика) — в
последнем случае сброс просто выполнится с небольшим опозданием при
следующем запросе/старте, а не строго в 00:00.

Чтобы изменить часовой пояс (например, если ваша команда живёт не по
Москве), задайте переменную окружения `WEEKLY_RESET_TZ` в виде
IANA-имени, например:
```
WEEKLY_RESET_TZ=Europe/Kyiv
```

## Деплой на Render

### 1. Загрузите проект в Git-репозиторий

Render разворачивает сервисы из Git (GitHub/GitLab). Если ещё не сделали:

```bash
git init
git add .
git commit -m "Initial commit"
```

Создайте пустой репозиторий на GitHub и запушьте туда код (`git remote add
origin ...` и `git push`).

### 2. Создайте Web Service на Render

Вариант А — через Blueprint (быстрее): зайдите в Render → **New +** →
**Blueprint**, укажите ваш репозиторий. Render найдёт `render.yaml` и
предложит создать сервис с уже прописанными переменными (значения с
`sync: false` нужно будет ввести вручную — `DATABASE_URL`,
`DISCORD_OWNER_ID` и Discord-ключи).

Вариант Б — вручную: **New +** → **Web Service** → выберите репозиторий →

- **Runtime**: Node
- **Build Command**: `npm install`
- **Start Command**: `npm start`
- **Plan**: Free (или платный, по желанию)

### 3. Заполните переменные окружения

В разделе **Environment** сервиса добавьте те же переменные, что и в
`.env.example` (см. таблицу ниже). Обязательно:

- `DATABASE_URL` — строка подключения из Neon (см. выше)
- `SESSION_SECRET` — длинная случайная строка (Render может сгенерировать
  сам, если использовать `render.yaml`)
- `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `DISCORD_REDIRECT_URI` —
  вход через Discord (redirect URI указывает на ваш домен на Render)
- `DISCORD_OWNER_ID` — ваш Discord ID, чтобы получить права владельца
- `NODE_ENV=production`

### 4. Примените схему БД и сид к продакшен-базе

Это нужно сделать один раз, **до первого открытия сайта** (или сразу
после первого деплоя). Проще всего — со своего компьютера:

```bash
# временно укажите в .env продакшен DATABASE_URL (строку из Neon,
# ту же, что вписали в Render), затем:
npm run setup
```

После этого можно вернуть в локальный `.env` вашу локальную строку
подключения — на продакшен-базу это не повлияет, `npm run setup` уже
создал в ней таблицы и роли.

Альтернативный способ — вкладка **Shell** у сервиса на Render (доступна
после первого деплоя): там тоже можно выполнить `npm run setup` — она
использует `DATABASE_URL`, уже прописанный в переменных окружения Render.

### 5. Деплой

Render автоматически соберёт и запустит сервис после пуша в ветку (или по
кнопке **Manual Deploy**). После завершения деплоя откройте выданный Render
URL (`https://<ваш-сервис>.onrender.com`) — должна открыться главная
страница сайта.

Не забудьте добавить `https://<ваш-сервис>.onrender.com/api/auth/discord/callback`
в **Redirects** приложения на Discord Developer Portal — иначе вход будет
падать с ошибкой `redirect_uri`.

> **Важно про диск:** контейнер Render не сохраняет файлы между деплоями и
> перезапусками. Поэтому все загружаемые картинки (аватары, иллюстрации к
> FAQ/правилам/регламенту) в этом проекте хранятся не на диске, а прямо в
> базе данных PostgreSQL — они не потеряются при передеплое.

## Роли и права доступа

В проекте три независимых понятия:

- **Роль(и) в иерархии** — сотруднику можно назначить **сразу несколько
  ролей** (в «Составе» или «Панели владельца» — чекбоксами). Сама иерархия
  (по приоритету, от высшей к низшей):
  Chief Event → Dep.Chief Event → Technical Administrator → Curator Event →
  Event Administrator → Chief Event Helper → Dep.Chief Event Helper →
  Senior Event Helper → Event Helper → Mini Event Helper. Хранится в таблице
  `user_roles` (многие-ко-многим, см. `src/db/schema.sql` и
  `src/db/roles.js`); `users.role_id` остаётся автоматически пересчитываемым
  кэшем **основной** (высшей по приоритету среди назначенных) роли — им
  по-прежнему пользуются сортировка/группировка в «Составе» и определение
  тира (helper/admin) для системы выговоров. Доступ к разделам личного
  кабинета (таблица ниже) даёт **любая** из назначенных ролей, а не только
  основная. Новый пользователь после первого входа через Discord ролей не
  имеет («Без роли») — администратор назначает их вручную в «Составе».
- **Видимость разделов личного кабинета** — настраивается по названиям
  ролей в `src/utils/roleAccess.js` (бэкенд, реальная проверка) и
  продублирована в `public/js/auth.js` → `Auth.ROLE_GROUPS` (фронтенд, для
  сайдбара). Сотрудники **без единой роли не видят в личном кабинете
  вообще ничего** — им показывается экран-заглушка «доступ появится после
  назначения роли». У сотрудников хотя бы с одной ролью доступ
  распределён так:

  | Раздел | Кто видит |
  |---|---|
  | Моя страница, Главная, FAQ, Состав, Правила МП, Регламент, Первые шаги | Любая роль (кроме «Без роли») |
  | Система выговоров (просмотр и выдача/удаление) | Chief Event, Dep.Chief Event, Technical Administrator, Chief Event Helper, Dep.Chief Event Helper, Senior Event Helper |
  | Заявки (анкета целиком, одобрить/отклонить/удалить) | Chief Event, Dep.Chief Event, Technical Administrator, Chief Event Helper, Dep.Chief Event Helper |
  | Кандидаты (только те, кого нужно обзвонить: имя, Discord, отметить прошёл/не прошёл обзвон) | Chief Event, Dep.Chief Event, Technical Administrator, Chief Event Helper, Dep.Chief Event Helper, Senior Event Helper |
  | Панель владельца | Chief Event, Dep.Chief Event, Technical Administrator |
  | Редактирование FAQ / Регламента / Правил МП / Первых шагов / Состава | Chief Event, Dep.Chief Event, Technical Administrator |

  Про «выдачу выговоров»: любая из перечисленных для этого раздела ролей
  видит полный список, но выдать выговор можно только сотруднику, чья
  **основная** (высшая по приоритету) роль **не выше** собственной — например,
  Dep.Chief Event Helper не может выдать выговор Chief Event Helper, а
  Dep.Chief Event — не может выдать выговор Chief Event. Владелец
  (`is_owner`) исключение — может выдавать выговор кому угодно. Удаление
  записей такому ограничению не подчиняется.

- **Флаг `is_admin`** сохранён в базе и в «Панели владельца» (можно
  выставлять другим пользователям), но с точки зрения перечисленных выше
  проверок доступа он больше ни на что не влияет — все узкие разделы и
  редактирование контента управляются только ролью из таблицы. Флаг
  `is_owner` — полный доступ ко всему, включая «Панель владельца», плюс
  подстраховка: владелец не теряет доступ, даже если у него по ошибке снята
  нужная роль.
- **Свой никнейм и аватар** может поменять сам себе любой сотрудник с
  ролью — кнопки на «Моей странице» (`PUT /api/auth/me/nickname` и
  `POST /api/auth/me/avatar`). Аватар/никнейм ДРУГОГО пользователя
  по-прежнему меняется только через «Состав» и требует роли из EDIT_ROLES
  (Chief Event / Dep.Chief Event / Technical Administrator).

Владелец назначается через `DISCORD_OWNER_ID` (см. [Как назначить
владельца](#как-назначить-владельца)) и автоматически получает высшую роль
(«Chief Event»). Все остальные входят через Discord самостоятельно и
остаются «Без роли» до тех пор, пока владелец/администратор не назначит им
роль и, при необходимости, права в «Составе» / «Панели владельца».

## Как устроены разделы

### Форматирование текста

Текст в разделах **FAQ**, **Регламент**, **Первые шаги** и в описании
каждого **правила** (МП) редактируется не обычным полем ввода, а
Markdown-редактором: панель инструментов (**Ж** жирный, **К** курсив,
зачёркнутый, заголовок, маркированный/нумерованный список, цитата, код,
ссылка на канал Discord) над обычным `<textarea>`, плюс переключатель
«Написать / Просмотр». Компонент — `public/js/markdownEditor.js`, работает
без внешних библиотек. Введённый Markdown-текст сохраняется как есть —
безопасным его делает не сохранение, а отображение: на бэкенде
(`src/utils/richText.js`) он рендерится через `markdown-it` и прогоняется
через `sanitize-html` с небольшим белым списком тегов (заголовки, жирный/
курсив/зачёркнутый, списки, цитаты, код, таблицы, `hr`, ссылки) — что бы ни
пришло в запросе к API напрямую, за пределы этого набора форматирование
выйти не может. Кнопка «Просмотр» запрашивает у бэкенда (`POST
/api/markdown/preview`) именно этот рендер, так что предпросмотр в
редакторе всегда совпадает с тем, что увидят на странице после сохранения.

Ссылки, вставленные через кнопку Discord (или просто написанные вручную в
виде `[название](https://discord.com/channels/…)`), при отображении
превращаются в фирменный "чип" — как упоминание канала в самом Discord.
Любая ссылка, ведущая не на discord.com/discord.gg, при отображении теряет
кликабельность и остаётся обычным текстом (проверка — `isDiscordChannelUrl`
в `src/utils/richText.js`, продублирована на фронте для мгновенной
подсказки в форме).

Записи, созданные до появления Markdown-редактора (обычный HTML из
прежнего `contenteditable`-редактора, а также совсем старый текст без
разметки), по-прежнему показываются корректно — формат определяется
автоматически (`renderBody` в `src/utils/richText.js`). При открытии такой
записи на редактирование её HTML лучшим возможным образом конвертируется в
Markdown-эквивалент (`rawBodyForEdit`/`legacyHtmlToMarkdown`) — жирный/
курсив/переносы строк/ссылка на Discord сохраняются, а кастомный размер и
гарнитура шрифта (их в Markdown нет) при первом же пересохранении этой
записи теряются.

### Публичный сайт

- **Главная** (`#/home`) — рассказ о роли Event Helper: что предлагает
  отдел, что требуется от кандидата, важная информация и кнопки перехода
  в Discord-сообщество (`https://discord.gg/eventsdenver`) и к форме
  заявки.
- **Оставить заявку** (`#/apply`) — прежде чем показать саму форму, страница
  требует предварительной авторизации через Discord (тот же OAuth2-флоу, что
  и вход в личный кабинет, см. «Личный кабинет» ниже, но с возвратом обратно
  на `#/apply` после подтверждения) — `Site.renderApplyAuthGate` в
  `public/js/site.js`. Отдельного текстового поля «Discord ID» в форме
  больше нет: ID берётся из уже подтверждённой Discord-сессии
  (`req.user.discord_id`, см. `POST /api/applications` в
  `src/routes/applications.js`) — так его не нужно вводить вручную и нельзя
  подделать или указать чужой. После авторизации показывается форма из семи
  обязательных полей (игровой Nickname и StaticID, возраст, среднесуточный
  онлайн, промежуток времени в игре, опыт, идеи по мероприятиям, мотивация),
  а над ней — от чьего Discord-аккаунта будет подана заявка, с возможностью
  выйти и авторизоваться другим аккаунтом («Не вы?»). Если задан
  `APPLICATIONS_WEBHOOK_URL`, в указанный Discord-канал сразу приходит
  уведомление о новой заявке с кликабельным упоминанием заявителя. Приём
  заявок можно временно закрыть (кнопка «Закрыть набор» в разделе «Заявки» —
  см. ниже): пока закрыт, вместо формы на `#/apply` показывается сообщение
  «Набор закрыт. Информация об открытии набора будет в наших новостях.» — и
  на всякий случай проверяется ещё раз на сервере при самой отправке
  (`GET`/`PUT /api/applications/status`, таблица `applications_settings`),
  чтобы форму нельзя было обойти прямым запросом к API.

### Личный кабинет

Доступен только сотрудникам с назначенной ролью (см. [«Роли и права
доступа»](#роли-и-права-доступа) выше) — у сотрудников «Без роли» вместо
сайдбара с разделами показывается экран с сообщением, что доступ откроется
после назначения роли.

- **Моя страница** — личная мини-страница сотрудника: его собственный
  счётчик мероприятий за неделю (с той же зелёной/красной подсветкой нормы,
  что и в «Составе»), список его собственных выговоров с лимитами по
  тиру — без доступа к чужим записям и без открытия полного раздела
  «Система выговоров» (тот виден только определённым ролям, см. таблицу
  выше) — и кнопки изменить свой собственный никнейм и аватар (доступны
  любому сотруднику с ролью, только для самого себя).
- **FAQ** — переключатель «Event Helper» / «Event Administrator» сверху,
  под каждым — свой текст и своя картинка. Переключатель и блок
  «Event Administrator» видны только сотрудникам тира «администраторы»
  (Chief Event, Dep.Chief Event, Curator Event, Event Administrator) и
  владельцу — тир «хелперы» видит только свой блок, без вкладок
  (`src/routes/content.js` не отдаёт им блок «administrator» вообще, не
  только скрывает вкладку на фронте). Кнопка «Редактировать» видна только
  ролям Chief Event, Dep.Chief Event и Technical Administrator.
- **Состав** — список всех сотрудников, отсортированный по иерархии (от
  Chief Event до Mini Event Helper). Справа от имени — счётчик мероприятий
  за неделю: зелёным, если ≥ нормы (по умолчанию 5, настраивается через
  `WEEKLY_EVENTS_TARGET`), красным — если меньше. Добавлять участников и
  менять роль(и)/счётчик/аватар может тот, кто видит кнопку «Редактировать» —
  роли Chief Event, Dep.Chief Event и Technical Administrator. Роль(и)
  выбираются чекбоксами — можно назначить сразу несколько. Клик по имени
  сотрудника (аватар + ник) открывает его **профиль** — карточка (роли,
  счётчик МП, статус блокировки) и полная история его выговоров с кнопками
  «Добавить выговор», «Разблокировать» и удаление отдельных записей — прямо
  из «Состава», без перехода в отдельный раздел. Виден тем же ролям, что
  видят «Систему выговоров» (см. таблицу выше и следующий пункт);
  `public/js/memberProfile.js`, `GET /api/reprimands/user/:id`.
- **Правила МП** — список правил, у каждого свой заголовок, текст (суть
  правила) и картинка; добавлять/редактировать/удалять может тот же
  список ролей — Chief Event, Dep.Chief Event и Technical Administrator.
- **Регламент** — так же, как FAQ: переключатель Event Helper / Event
  Administrator, свой текст и картинка на каждую аудиторию; то же
  ограничение видимости вкладки «Event Administrator» по тиру (см. FAQ выше).
- **Первые шаги** — один текст + одна картинка, без переключателя.
- **Система выговоров** — видна ролям из таблицы выше: список
  дисциплинарных записей на сотрудников с причиной и датой. Любая из этих
  ролей может добавлять и удалять записи, но **выдать** выговор можно
  только сотруднику с ролью не выше своей (см. пояснение в разделе
  [«Роли и права доступа»](#роли-и-права-доступа) выше;
  `src/routes/reprimands.js`, `POST /api/reprimands`). Тот же просмотр
  истории и выдача/удаление доступны и точечно — по одному сотруднику —
  через клик на него в «Составе» (см. пункт выше), это тот же самый API,
  просто другая точка входа. Правила расчёта
  баллов и автоблокировки — в `src/utils/reprimandRules.js`:
  - **Хелперы**: устный выговор = 1 балл, строгий = 2 балла. При
    достижении **4 баллов** учётная запись **блокируется автоматически**
    (личный кабинет закрывается целиком, как и для «Без роли»). Как
    только у сотрудника набирается **2 непогашенных устных**, они
    **автоматически объединяются в 1 строгий** — устные при этом остаются
    в истории (помечены как «объединён»), просто больше не считаются
    отдельно. Правило объединения действует только у хелперов.
  - **Администраторы**: баллы («point»), максимум **3**, тоже ведут к
    автоблокировке при достижении. Каждый балл автоматически перестаёт
    учитываться через 10 дней после выдачи — если из-за этого баллы
    опускаются ниже лимита, блокировка снимается сама (пере-проверяется
    при каждом входе заблокированного пользователя, см. `attachUser` в
    `src/middleware/auth.js`).
  - **Блокировка никогда не удаляет пользователя или его выговоры** — только
    закрывает доступ в личный кабинет (`users.is_blocked`). Снять её вручную
    может любая роль из таблицы выше кнопкой «Разблокировать» в карточке
    сотрудника (`POST /api/reprimands/users/:id/unblock`).
- **Заявки** — видна только ролям из таблицы выше: список заявок, поданных
  через публичную форму «Оставить заявку» (со всей анкетой — возраст, опыт,
  идеи, мотивация и т.п.), с возможностью одобрить/отклонить/удалить, плюс
  переключатель «Закрыть набор» / «Открыть набор» в шапке раздела (виден тем
  же ролям) — закрывает публичную форму подачи заявки на сайте, см. выше.
  Senior Event Helper этот раздел не видит вообще.
- **Кандидаты** — отдельный, более узкий раздел: заявки, которые уже
  одобрили и которые ждут результата обзвона. Показывает только имя,
  Discord и дату одобрения (саму анкету с личными данными не показывает) и
  две кнопки — «Прошёл обзвон» (кандидат становится сотрудником с ролью
  Mini Event Helper) и «Не прошёл обзвон» (кандидат снимается с
  рассмотрения). Виден ролям из таблицы выше — это единственный из двух
  разделов, который видит Senior Event Helper: он занимается именно
  обзвоном одобренных кандидатов, но не имеет доступа к самим заявкам
  (`CANDIDATES_ROLES` в `src/utils/roleAccess.js`,
  `GET /api/applications/candidates`).
- **Панель владельца** — только роли Chief Event, Dep.Chief Event и
  Technical Administrator (плюс аккаунт с флагом `is_owner`): список всех
  аккаунтов, назначение роли(ей)/прав администратора и владельца, удаление.

## Переменные окружения

| Переменная | Обязательна | Описание |
|---|---|---|
| `DATABASE_URL` | да | Строка подключения к PostgreSQL (Neon) |
| `SESSION_SECRET` | да | Случайная строка для подписи сессий |
| `DISCORD_CLIENT_ID` / `DISCORD_CLIENT_SECRET` / `DISCORD_REDIRECT_URI` | да | Вход через Discord — без них зайти в личный кабинет нельзя |
| `DISCORD_OWNER_ID` | рекомендуется | Discord ID аккаунта, который автоматически получает права владельца при входе |
| `APPLICATIONS_WEBHOOK_URL` | нет | Discord Webhook для уведомлений о новых заявках |
| `CLOUDINARY_URL` (или `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET`) | нет | Хранить аватары в Cloudinary вместо базы, см. [«Аватары через Cloudinary»](#аватары-через-cloudinary-опционально) |
| `DISCORD_BOT_TOKEN` | нет | Включает бота учёта посещаемости мероприятий, см. [соответствующий раздел](#discord-бот-учёта-посещаемости-мероприятий) |
| `DISCORD_EVENTS_CHANNEL_ID` | нет | Канал, за которым следит бот учёта посещаемости (по умолчанию `1446581838100430878`) |
| `DISCORD_EVENTS_SOURCE_BOT_ID` | нет | Чьи сообщения о сборах читает бот учёта посещаемости (по умолчанию `1468289401795903690`) |
| `EVENT_BOT_CATCHUP_LIMIT` | нет | Сколько последних сообщений канала проверять при старте (по умолчанию `50`) |
| `APP_TITLE` / `APP_SUBTITLE` | нет | Название отдела, отображается в личном кабинете |
| `WEEKLY_EVENTS_TARGET` | нет | Норма мероприятий в неделю (по умолчанию 5) |
| `WEEKLY_RESET_TZ` | нет | Часовой пояс (IANA, например `Europe/Moscow`) для еженедельного сброса счётчика «МП в неделю» по понедельникам в 00:00 (по умолчанию `Europe/Moscow`) |
| `PORT` | нет | Порт сервера (Render подставляет автоматически) |
| `NODE_ENV` | нет | `production` на хостинге — включает secure-cookies |

## Частые проблемы

**«password authentication failed» / ошибка SSL при подключении к базе.**
Проверьте, что `DATABASE_URL` скопирован из Neon целиком, включая
`?sslmode=require`, и без лишних пробелов/переносов строк.

**После деплоя открывается пустая страница или ошибка 500.**
Скорее всего, схема ещё не применена к продакшен-базе — выполните
`npm run setup`, указав продакшен `DATABASE_URL` (см. «Деплой на Render»,
шаг 4).

**Кнопка «Войти через Discord» неактивна.**
Значит `DISCORD_CLIENT_ID`/`DISCORD_CLIENT_SECRET` не заданы на сервере —
добавьте их в `.env` (локально) или в Environment (на Render) и
перезапустите сервис.

**Вход через Discord падает с ошибкой `redirect_uri`.**
`DISCORD_REDIRECT_URI` в переменных окружения должен **точно** совпадать
(включая `http`/`https` и путь) со значением, добавленным в **Redirects**
на странице OAuth2 вашего приложения в Discord Developer Portal.

**Я вошёл через Discord, но нет прав владельца.**
Проверьте, что `DISCORD_OWNER_ID` в переменных окружения совпадает с вашим
реальным Discord ID (числовой ID, не username), и войдите заново — права
синхронизируются при каждом входе. Также можно выполнить `npm run db:seed`
после того, как переменная задана правильно — это назначит владельца, если
вы уже когда-то входили.

**Картинки не сохраняются между деплоями на Render.**
Такого быть не должно — все картинки хранятся в самой базе PostgreSQL
(таблица `images`), а не на диске контейнера. Если картинка пропала,
проверьте, что `DATABASE_URL` в переменных окружения Render не менялся
(иначе сервис фактически «переключился» на другую базу).
